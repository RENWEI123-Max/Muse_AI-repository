# D7 backend handoff

No deployment was performed. Apply migrations through the existing migration runner before starting the new server; 004 grants the runtime role access to all added objects. D2's four business tables already contain all architecture columns; 004 adds persistent request responses, sending leases, chat scheduling slots and a polling offset. Nullable outbox chat_id permits an explicit failed record for an unbound user.

Muse must inject `BIZHANG_TELEGRAM_BOT_TOKEN` into the process environment for this dedicated bot. The implementation reads it only there, never from a file. Inject `BIZHANG_TELEGRAM_BOT_USERNAME` without `@` for deep links. Without a valid username, bind-token returns its one-time token as bind_url with bot_configured=false. Without the bot credential, polling/sending loops do not start; CRUD/evaluation still work. Never use another bot's configuration.

Alert API prefix is `/api/v1`. List returns alerts with current_price_usd, price_status and alerts_paused. POST returns alert plus triggered_immediately and persists the original response per user/UUID Idempotency-Key. PATCH requires the raw version string in If-Match. DELETE soft deletes without If-Match. IDs, generations, versions, amounts and attempt counts are JSON strings. Events retain delivery_status and last_error even after soft deletion. Binding GET returns only chat_id_last4, never a full chat ID.

Initial alert delivery is eligible after 2 seconds. Attempts 2–5 are scheduled after 8, 30, 120 and 600 seconds following the preceding failed attempt; five completed send attempts end in failed. This applies all five architecture intervals to five total attempts. A valid 429 retry_after overrides the ordinary interval and delays every pending send to that chat. Delayed rows are rescheduled rather than blocking other chats. The worker checks every 250 ms, so scheduled times are earliest eligible times, not hard real-time promises.

An unbound alert still triggers/auto-disables and records one event plus a failed outbox row with TELEGRAM_NOT_BOUND. Binding later does not replay old triggers. Unbind revokes the whitelist and cancels pending/sending delivery records; a send already in progress completes before unbind commits. Bind acknowledgements use the same queued/rate-limited sender. Unknown messages/chats receive nothing.

Claimed deliveries commit sending_at and a unique lease before transport invocation. The send transaction holds the binding and outbox row locks. Recovery requeues abandoned sending leases older than 60 seconds while skipping locked active sends. A process death may cause duplicate Telegram delivery; it never re-evaluates or re-creates the event. Rate slots and getUpdates offset survive process restarts. getUpdates runs under a database advisory lock, with 30-second polls, 35-second transport timeout and 5/10/30/60-second failure backoff.

`npm test` requires PostgreSQL binaries initdb/pg_ctl on PATH. The integration test creates a new temporary cluster with an isolated Unix socket, applies all migrations, uses only fake transports, SIGKILLs a child sender for crash testing, and destroys the cluster afterwards. It never imports application db.js or loads connection configuration. On macOS a sandbox may require permission for PostgreSQL shared memory. No live Bot integration has been performed.
