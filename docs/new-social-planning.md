## (a) 向 Smith 追问的关键问题（8 个）

### Q1 目标人群、地区和语言
**问**：首发哪些国家/地区？界面支持哪几种语言？目标用户是什么人（年龄段、性别比例、是想交朋友、练外语，还是找对象）？是否跨国匹配（例如韩国用户匹配美国用户）？

**为什么必须问**：
- 服务器部署地点由地区决定。sg-claude 在新加坡，覆盖韩国、日本、东南亚时延迟可以接受；如果主打美国、欧洲或中东，单个新加坡节点的视频延迟和丢包体验会很差，要么多地部署，要么改用云服务（见 (b) 第 3 节）。
- 合规由地区决定：韩国的交友类服务要做成人认证（본인인증），欧盟要满足 GDPR/DSA，美国有 CSAM 上报义务和各州的年龄验证法案，中国大陆不能用 CallKit。
- 用户池能不能“热起来”也取决于地区：交友类最怕冷启动，用户分在太多国家和语言里，每个人能刷到的资料、等到的互相喜欢都会很少。

**不知道会卡住什么**：服务器选址、实名/成人认证方案、语言包、隐私政策写法、上架地区。

### Q2 核心玩法：怎么认识陌生人
**问**：用户主要通过哪种方式认识人？(1) 一点“开始”就随机连上视频或语音（即时随机）；(2) 先刷资料卡，双方都喜欢再通话（先匹配后通话）；(3) 先文字聊天，熟了再升级成语音/视频。可以多选，但要排出 MVP 先做哪个。

**为什么必须问**：
- 这决定了首页长什么样、后端的核心是“实时匹配队列”还是“推荐 + 喜欢”，也决定了审核压力有多大。
- **方式 (1) 与 iOS 上架直接冲突**：App Store 审核指南 1.2 写明，主要用于“Chatroulette 式体验、随机或匿名聊天”的 App 不属于 App Store，可能被不经通知下架。这是对产品形态本身的限制，加审核措施消除不了。所以要请 Smith 在 (2)(3) 或 (b) 第 0 节的替代方案里选定 iOS 核心玩法；如果坚持即时随机，必须同时接受 iOS 版不能以它为核心（见 (b) 第 0 节的决策门槛）。

**不知道会卡住什么**：首页和核心循环、匹配服务设计、Muse 的 UI 规划，三方都没法开工；上架可行性门槛（(b) 第 0 节）过不去。

### Q3 视频和语音的形式：随机 1v1，还是语音房 / 直播间
**问**：MVP 只做 1v1（双方确认后的通话、好友互拨），还是也要多人语音房、视频直播间、连麦、打赏？如果 Smith 原本想要的是“随机 1v1”，见 Q2：iOS 上它不能作为主要体验。

**为什么必须问**：
- 1v1 与多人房 / 直播是两种不同的产品：后者要做房间管理、主播体系、礼物、CDN 分发和更重的实时审核，开发量至少翻倍。
- 服务器带宽成本也完全不同：1v1 每通话是 2 路流，直播间是 1 路上行加 N 路下行。

**不知道会卡住什么**：技术路线（LiveKit 能否撑住直播规模）、带宽和服务器预算、页面清单。

### Q4 和 MauGo 的关系：为什么不直接在 MauGo 里加视频
**问**：新社交是独立 App、独立账号体系吗？跟 MauGo 共享用户池吗（MauGo 用户能否一键登录、互相匹配）？品牌、开发者账号要分开吗？

**为什么必须问**：
- Claude 的判断是**应该独立做**，理由有三条：(1) MauGo 的定位是“慢节奏写信”，与即时视频的调性冲突；(2) App Store 审核指南 1.2 明确把以“Chatroulette 式体验、随机或匿名聊天”为主要用途的 App 列为不属于 App Store、可能不经通知下架，把即时视频（尤其随机匹配）加进 MauGo，会让已经做好的 MauGo 也承担这个风险；(3) 两者的审核压力、年龄分级和运营节奏都不同。
- 但是否共享账号或用户池是商业决定：共享可以缓解冷启动，代价是两边账号、注销、数据导出要联动。

**不知道会卡住什么**：后端是从 MauGo fork 一份独立部署，还是在 MauGo 后端里加模块；数据库是否共用；隐私政策是一份还是两份。

### Q5 平台优先级：iOS 原生优先，还是沿用 H5 + Capacitor
**问**：先上 iOS、Android 还是双端？是否接受沿用 MauGo 的 Vue 3 + Capacitor 方案（通话部分加原生插件），还是希望像「币账」一样做 iOS 原生？

**为什么必须问**：
- 视频通话在 WKWebView 里能跑 WebRTC，但美颜、后台保活、来电唤醒（PushKit + CallKit）、发热和耗电控制，原生明显更好。
- 团队现有资产是 H5（MauGo，回归 69/69）加 iOS OC 原生（币账，D1 架构刚做完）。选 H5 能复用最多 MauGo 代码；选原生则 Android 要另做一套。
- Claude 的建议见 (b) 第 3.3 节：MVP 用 Capacitor，通话层先用 WebView 里的 LiveKit JS，好友来电需要时再补原生插件。

**不知道会卡住什么**：开发语言、工程结构、Codex 审核环境（iOS 原生验收需要 Mac 和模拟器/真机）。

### Q6 变现方式
**问**：靠什么赚钱？候选有：订阅会员（筛选性别/地区、无限匹配、回看错过的人）、按次付费（每次匹配或每分钟扣钻石）、礼物打赏（主播分成）、广告。是否沿用 MauGo 的“钻石 + Pass”体系？

**为什么必须问**：
- 虚拟商品必须走苹果内购（指南 3.1.1）。只要有礼物打赏、主播分成，就涉及提现、税务和反洗钱，复杂度跳一级。
- “付费筛选异性”是这类 App 的常见变现点，但会激化性别比例失衡，需要 Smith 做取舍。
- 变现方式还决定钱包账本要不要支持按分钟扣费（通话中途余额不足怎么处理）。

**不知道会卡住什么**：商品目录、App Store Connect 商品配置、钱包和账本设计、会员页 UI。

### Q7 安全审核机制和运营资源
**问**：谁来做人工审核？是否有 7×24 小时审核人员（自建或外包）？预算能否接入第三方内容识别服务（视频画面涉黄识别、语音转文字审核）？是否强制人脸认证 / 实名认证后才能视频？举报后多久内要处理？

**为什么必须问**：
- 陌生人视频是 App Store 审核和监管的重点（随机/匿名形态本身就被指南 1.2 排除，见 Q2）。没有实时审核、快速封禁、可追溯证据，上架大概率被拒，上线后也可能被下架。
- 审核方案直接决定产品形态，比如“视频前几秒模糊”“新账号先只能语音”“认证用户才能开视频”。
- 第三方识别服务按调用量收费，会把视频画面送到外部服务，必须写进隐私政策。

**不知道会卡住什么**：审核后台、举报证据留存设计、隐私政策、上架材料（审核说明里要写清审核机制）。

### Q8 主体、账号和基础设施由谁提供
**问**：用哪个公司主体和 Apple 开发者账号上架？HTTPS 域名、TURN 用的公网 IP 和带宽、短信/邮箱服务、法律文本（隐私政策、服务条款、EULA、社区准则）由谁、什么时候提供？首期服务器和带宽预算大概多少？

**为什么必须问**：MauGo 的大部分阻塞都卡在这里：D10 语音等域名，D9 内购等 Apple 配置，SMTP 未配置导致验证码收不到，Figma 无权限，法律文本一直是占位。新项目的通话**必须**有 HTTPS 域名和 TURN 才能在真机上跑通，这一项要第一天就定。

**不知道会卡住什么**：真机联调、内购、上架提交，以及所有“外部配置缺失 503”类阻塞。

## (b) 初步产品概念

以下内容基于这些【假设】（Smith 回答 Q1–Q8 后修订）：
- 首发韩国 + 东南亚英语用户，界面英文和韩文，沿用 MauGo 的语言组合，sg-claude 地理上也合适。
- 核心玩法是**先看资料、双方互相喜欢后再通话**（见第 0 节方案 A）：通话只发生在已互相确认的两个人之间，而且需要对方接受邀请。**不做即时随机 1v1**，原因见第 0 节。
- MVP 不做多人语音房和直播。
- 独立 App、独立账号和数据库；后端从 MauGo 复用模式和部分模块，不和 MauGo 共用库。
- 先上 iOS，Capacitor 工程同时保留 Android。
- 变现用钻石（苹果内购）+ 会员订阅（筛选、无限次数）；不做礼物打赏和主播分成。
- 仅限 18+。

### 0. 开发前决策门槛：iOS 上架可行性

**限制原文**（[App Store 审核指南 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)，2026-11-15 查阅）：含用户生成内容的 App，如果“end up being used primarily for pornographic content, Chatroulette-style experiences, random or anonymous chat, …”，则“do not belong on the App Store and may be removed without notice”。

**这意味着什么**：
- 被排除的是**产品形态**（以随机或匿名聊天为主要体验），不是“审核做得不够”。过滤、举报、拉黑、实时识别、18+ 门槛是 1.2 对所有 UGC App 的基本要求，做全了也不能让“随机 1v1 为核心”变成合规形态。原稿把它写成“可能下架、靠审核说明争取通过”是不准确的，本版更正。
- 即使上架时侥幸通过，指南写的是“may be removed without notice”，上线后随时可能被下架，账号也可能受牵连（指南 1.2 后段：严重或反复违规可被移出开发者计划）。

**替代概念**（都满足“不随机、不匿名、双方确认后才通话”）：

| 方案 | 怎么认识人 | 什么时候能通话 | 评价 |
| --- | --- | --- | --- |
| **A 先看资料、互相喜欢后通话**（Claude 建议作 MVP） | 浏览带真实头像的资料卡，喜欢/跳过 | 双方互相喜欢 → 成为好友 → 一方发通话邀请、对方接受 | 形态最接近成熟交友 App；与 MauGo `unlocked_at` 的“双方确认才解锁”账本一致，后端复用最多 |
| B 先文字、再升级通话 | 同 A，或 MauGo 式开场白 | 文字往来达到门槛（【假设】双方各发过若干条）后，双方都点“同意通话”才解锁 | 安全性最好，但到第一通电话的路径更长 |
| C 话题/时段预约通话 | 用户报名同一话题或语言练习时段，系统列出候选人的资料 | 看过资料、双方都确认后才建立通话 | 适合“练外语”定位；需要排期和到场提醒 |
| D 即时随机 1v1（原稿假设） | 一点开始即随机连线 | 立即 | **不建议作为 iOS 核心体验**；如果 Smith 坚持，只能考虑 iOS 以外的渠道，或者作为非核心的次要功能并接受被拒/下架风险，需 Smith 明确决定 |

A/B/C 的共同要求：资料实名化（真实头像、昵称、认证标识），不提供匿名身份；通话前对方资料可见；任何一方都能拒绝或撤回。

**门槛规则**（建议写进第一阶段里程碑的第 1 步）：
1. Smith 在 A/B/C/D 中选定 iOS 核心玩法；选 D 必须书面接受上述风险。门槛通过前，匹配/通话相关的产品设计和开发不开工。
2. Muse 的产品设计、Codex 的审核清单都把“核心路径里没有随机或匿名连线”作为必查项。
3. 指南条文的适用由 Apple 个案判断【待核实】：可以在立项后通过 Apple 的 “Meet with App Review” 咨询，或尽早用最短链路提交 TestFlight 外部测试审核，在全量开发前拿到反馈。

### 1. 核心循环（从打开到聊上天的最短路径）

目标（按方案 A）：新用户首次打开后 2 分钟内完成建档并看到第一批资料卡；互相喜欢后，发起通话邀请只需 1 次点击。代价是第一通电话取决于对方何时回应，比随机连线慢，这是为上架可行性做的取舍。

```
首次打开
 → 18+ 年龄申报 + 同意社区准则（一屏，不可跳过）
 → 注册/登录（Apple 登录 / 邮箱；手机号视 Q1 地区而定）
 → 资料：昵称 + 性别 + 出生日期 + 语言 + 至少 1 张真实头像（先看资料的前提，不允许匿名）
 → 首页资料卡：头像、昵称、国家、语言、简介、可选 10 秒语音介绍
 → 喜欢 / 跳过（每日免费喜欢次数，会员加量或解锁筛选）
 → 双方互相喜欢 → 成为好友（解锁）→ 文字聊天
 → 任一方点「语音」或「视频」发出通话邀请
 → 系统请求麦克风（视频再加摄像头）权限
 → 对方在 App 内收到邀请，接受 / 拒绝（拒绝不通知原因）
 → 通话建立
    · 视频：首次视频通话前 N 秒画面模糊（【假设】N=3–5，双方都点「显示」才清晰）
    · 语音：直接通话
 → 通话中：挂断 / 静音 / 关摄像头 / 举报（一键）/ 拉黑
 → 通话后：举报 / 拉黑 / 继续聊天
```

可留存的点：好友关系（类似 MauGo 的 `unlocked_at`，双方互相喜欢即解锁）、每日免费喜欢次数（类似 MauGo 每日 10 次免费收取）、会员的筛选特权。

新账号的安全节奏【假设，需 Q7 确认】：新注册账号先只能文字和语音；完成人脸认证（活体检测）后才解锁视频并获得“已认证”标识。

### 3. 视频和语音的技术路线

#### 3.1 建议：沿用 LiveKit 自建，部署在 sg-claude，作为 MVP 方案

理由：
- **团队经验和选型已经有了**：MauGo 的语音通话上线范围里就选了 LiveKit 自建在 sg-claude。【待核实】本仓库目前没有 LiveKit 相关代码或配置（MauGo D10 语音“未开始”，卡在域名）。所以说“复用”，复用的是选型、部署方案和对接经验，没有现成代码。
- **1v1 场景很适合**：1v1 通话本质是“两人一个房间”。LiveKit 的房间 + 访问令牌模型很直接：对方接受邀请后，后端校验双方是好友且未互相拉黑，签两个 token，客户端各自加入；通话结束删除房间。
- **开源，没有按分钟计费**：成本只有服务器和带宽，数据也在自己手里，方便做合规（证据留存、跨境数据说明）。
- **能跑在 Capacitor 里**：`livekit-client`（JS SDK）可以在 WKWebView 中运行（iOS 14.3+ 支持 WebRTC）；需要原生能力时有官方 Swift/Android SDK 可替换。
- **审核需要的能力它有**：服务端可以订阅轨道或用 Egress 抽帧/录制，用于涉黄识别和举报证据；Webhook 能拿到房间和参与者事件，用来做通话计时和计费。

前置条件（缺一个真机就跑不通）：
- HTTPS 域名 + TLS 证书（MauGo D10 就卡在这里，见 Q8）。
- TURN：LiveKit 内置 TURN，要开 443/TLS 和 UDP 端口段。韩国和东南亚不少移动网络、公司网络会挡 UDP，没有 TURN/TLS 会有一部分用户连不上。
- 带宽：每路 720p 视频约 1–1.5 Mbps，经 SFU 中转，一通 1v1 约占服务器 2 路上行 + 2 路下行。sg-claude 的带宽上限和计费方式【待核实】，它决定能同时承载多少通话。
- sg-claude 已经在跑 Codex 审核等服务，生产媒体服务器建议独立机器，至少独立容器并限制资源【假设】。

#### 3.2 什么时候换方案

| 情况 | 建议 |
| --- | --- |
| Q1 回答主打美国/欧洲/中东，或跨洲匹配 | LiveKit 多区域自建运维成本高，改用 LiveKit Cloud（同一套 SDK，迁移成本最低）；或改用 Agora / ZEGO / 腾讯 TRTC 这类全球节点覆盖好的商业服务 |
| Q3 回答要做直播间、大规模语音房 | 商业 RTC（Agora / ZEGO / TRTC）自带直播 CDN、美颜、内容审核插件，自建的总成本反而更高 |
| 需要成熟美颜/滤镜（交友视频的常见留存点） | 商业 RTC 或第三方美颜 SDK（收费），LiveKit 本身不带 |
| 预算紧、想最快验证 | 维持 LiveKit 自建：只要 1 台服务器，没有按分钟费用 |

不建议纯 P2P（不经过 SFU，直接用 WebRTC）：省带宽，但会暴露双方 IP（陌生人社交的隐私风险），服务端也拿不到媒体流，做不了审核抽帧和证据留存。

#### 3.3 客户端通话层

- **MVP**：Capacitor + `livekit-client` 在 WebView 中运行。通话邀请只在对方 App 处于前台时投递（不在线时提示“对方不在线，已留言”），**不需要 VoIP 来电推送**，因此 MVP 可以不做 CallKit/PushKit，最大化复用 MauGo 的 H5 代码。
- **第二阶段（离线来电）**：要让对方 App 在后台或被杀掉时也能响铃，iOS 上只能用 PushKit VoIP 推送，而且苹果要求收到 VoIP 推送后必须立即上报 CallKit。这部分要写原生插件（新增依赖，需批准），此时评估是否把整个通话层换成 LiveKit Swift SDK。中国大陆区不允许使用 CallKit，若上架中国区需另行处理【待核实，取决于 Q1】。
- 如果 Q5 定为 iOS 原生：通话直接用 LiveKit Swift SDK + CallKit，可借鉴币账的原生工程经验，但 Android 需另做。

#### 3.4 后端新增的核心服务（概念，不是实现）

- **推荐与喜欢**：按语言、筛选条件（会员）出资料卡；已拉黑（复用 MauGo `user_blocks` 双向生效规则）、已跳过、已封禁的不出现；互相喜欢在同一事务里写入好友关系，双向同时喜欢要做并发测试（MauGo B3 死锁的教训）。
- **通话邀请与会话**：校验双方是好友、未拉黑、视频需已认证 → 建通话记录 → 对方接受后签 LiveKit token（短时效、只允许进入这一个房间）→ Webhook 记录开始/结束时间 → 计入免费次数或扣钻石（沿用 MauGo 的幂等键 + 同事务记账）。
- **好友关系**：双方互相喜欢 = 好友，作为唯一的聊天/互拨权限账本（类比 MauGo `conversations.unlocked_at`）。

### 4. Apple 交友类 App 18+ 新规与安全合规要点

> 以下规则以提交时 App Store 审核指南和 App Store Connect 的最新版本为准，【待核实】。各国法律要点需要当地律师确认，Claude 只列出必须查的方向。

#### 4.1 App Store 审核要点
- **先区分两件事**：
  - **产品自行限定成人**：注册门槛、出生日期申报、拒绝未满 18 岁、疑似未成年冻结（4.2 节）。这是我们自己的产品规则，由我们执行和留档。
  - **平台强制分级**：在 App Store Connect 年龄分级问卷里如实申报，由 Apple 据此给出 App Store 上的分级。两者都要做，互不替代。
- **2026-11 交友类新规**（[Apple 官方公告 “Upcoming: New age rating content descriptors in App Store Connect”，2026-11-02](https://developer.apple.com/news/?id=yxkh08us)）：
  - **生效日期**：2026-11-16 起，年龄分级问卷新增两项声明：**Shared Location**（与他人或群组分享真实位置）和 **Dating and Relationships**（让真实用户之间建立约会或关系连接的功能，或与用户进行性/恋爱内容互动的虚拟伴侣）。
  - **申报时机**：提交 App 更新或修改年龄分级问卷时必须填写；**所有 App 须在 2027-01-12 前完成这两项声明**。
  - **分级后果**：包含 Dating and Relationships 的 App **最低分级为 18+**。Shared Location 在部分地区不一定影响最低分级；巴西当地法规要求 Shared Location 为 A16、Dating and Relationships 为 A18。
  - **对本项目的适用**：新社交的核心就是让真实陌生人建立联系并通话，Claude 判断应勾选 **Dating and Relationships**，平台强制最低 18+；即使 Smith 定位为“交朋友 / 练外语”，也不应据此不勾选【最终按问卷说明核对】。MVP 只显示国家、不分享实时位置，Shared Location 不勾选；以后如果加“附近的人”或位置分享，要重新申报。新项目首次提交必然晚于 2026-11-16，所以第一次提交就要填。
  - **顺带提醒（超出本任务范围）**：MauGo 同样是交友类 App，也要在 2027-01-12 前补这两项声明。
- **2025 年分级调整**：Apple 2025 年已把分级改为 4+/9+/13+/16+/18+ 并更新问卷（用户生成内容、私信/聊天等问题），2026-11 的新声明是在这套问卷上增加的。
- **Declared Age Range API**（iOS 26 起）：可以获取系统提供的年龄区间。建议接入，用来补充自行申报，并应对美国部分州（如得州、犹他州）的 App Store 年龄验证法案【待核实生效范围】。
- **指南 1.2 用户生成内容**，必须具备：内容过滤机制、举报入口并及时处理、拉黑功能、公开的联系方式。另外，主要用于 Chatroulette 式体验、随机或匿名聊天的 App 不属于 App Store，可能不经通知下架——这是产品形态限制，靠审核措施无法消除，处理方式见 (b) 第 0 节决策门槛。在核心玩法已改为“双方确认后通话”的前提下，提交审核时仍要在审核说明里写清楚：双方确认机制、审核流程、实时识别、封禁机制、仅限 18+，并提供测试账号和演示视频。
- **指南 5.1.1(v)**：必须能在 App 内注销账号（复用 MauGo B9）。
- **指南 4.8**：如果提供第三方登录，要同时提供 Apple 登录或符合要求的同类登录。
- **指南 3.1.1**：钻石、会员都必须走内购；订阅需展示价格、周期、自动续费说明，并附服务条款和隐私政策链接。
- **隐私清单**：App Store 隐私标签申报摄像头/麦克风/照片/位置；`Info.plist` 写清摄像头和麦克风的用途说明；隐私清单（Privacy Manifest）需覆盖所用 SDK。

#### 4.2 实名 / 年龄 / 未成年保护
- 注册时自行申报出生日期，不满 18 岁直接拒绝（复用 MauGo E3 的 18+ 申报留档）。
- **人脸活体认证**：解锁视频的门槛。可选第三方（如 AWS Rekognition Face Liveness、Yoti、FaceTec 等）；同时可做年龄估计，拦截明显未成年【需 Q7 预算】。
- 韩国：交友类服务通常被要求做成人认证（PASS 等本人认证），而且必须由有资质的韩国认证服务商提供【待核实，需律师确认】。
- 疑似未成年的举报要最高优先级处理，立即冻结账号、人工复核。

#### 4.3 举报、拉黑与实时审核
- **一键举报**（通话中和通话后都可以）：自动附带最近几秒的截帧作为证据（需在服务条款与隐私政策中告知，仅在举报时上传），复用 MauGo B7/B13 的举报 + 附件模型。
- **拉黑**：双向生效，拉黑后不再出现在对方资料卡里、互相不可见、不能互发邀请（复用 MauGo `user_blocks`）。
- **实时识别**：视频定时抽帧送涉黄/暴力识别；命中后立即断开通话、封禁账号并进入人工复核。文本沿用 MauGo E3 的内容过滤（422）。
- **视频模糊前置**：开头几秒画面模糊、双方确认后清晰；用户也可以在设置里选择“始终先模糊”。
- **封禁**：账号 + 设备级封禁（防止注销重注册）；被举报次数阈值自动临时限制。设备标识的采集方式要符合 Apple 规定（不得用于跨 App 追踪）【待核实】。
- **CSAM**：如果在美国上架，发现儿童性剥削内容有向 NCMEC 上报的法定义务，必须有处理流程【待核实】。
- **审核后台和人员**：举报队列 SLA（建议举报 24 小时内处理，涉未成年/涉黄立即处理），运营人员 7×24 或至少覆盖目标地区的活跃时段（Q7）。

#### 4.4 隐私
- **默认不录制通话**；只在举报时上传证据截帧，或在识别命中时留存，存储期限明确（例如 90 天）并写进隐私政策。
- 匹配卡片只显示昵称、国家、语言，不显示精确位置和年龄；媒体流经 SFU 中转，不暴露对方 IP。
- 数据导出和注销（复用 MauGo B9）；注销后匹配记录、好友关系、证据按政策处理。
- 跨境传输：服务器在新加坡，用户在韩国/欧盟时，隐私政策要写明跨境传输；欧盟用户还要满足 GDPR 和 DSA（举报处理透明度等）【待核实，取决于 Q1】。
- 第三方服务（活体认证、内容识别）会处理人脸和画面，要逐个写进隐私政策和隐私标签。

#### 5.4 MauGo 的经验教训（新项目第一周就要处理）
1. **外部依赖第一天就要**：MauGo 卡最久的都不是代码，而是域名（D10）、Apple 配置（D9 沙盒、StoreKit）、SMTP、Figma 权限、法律文本占位。新项目先列外部依赖清单，由 Smith 指定提供人和日期（Q8）。
2. **先打通真机最短链路，再铺页面**：MauGo 先把 189 个状态逐个做完，C7 MVP 整体验收却没通过。新项目建议第一个技术里程碑是“两台真机上，两个已互相喜欢的账号通过 sg-claude 的 LiveKit 完成一次邀请 → 接受 → 视频通话”，再扩展其他页面。
3. **并发与锁要早测**：MauGo B3 双向并发开场白曾经死锁（最后改用 `FOR NO KEY UPDATE` 解决）。双方同时互相喜欢、同时互发通话邀请都是同类场景，并发测试要从第一版就写。
4. **账号隔离从第一版就做**：MauGo F07（聊天草稿没有按账号隔离）是后补的问题，新项目本地存储的键一开始就带用户 ID。
5. **视觉源要可访问**：Figma 无权限导致 D4/D5/D6/D11 视觉验收全部 blocked。新项目设计稿要确保 Muse/Codex/Claude 都能访问。
6. **不伪造**：后端没有的能力不要 mock 成功（MauGo D9 的 StoreKit 如实标“未通过”），这条继续保持。
7. **上架规则先于功能**：本项目原稿曾以即时随机 1v1 为核心，与指南 1.2 冲突。今后新玩法先对照审核指南做可行性判断，再进入设计。
